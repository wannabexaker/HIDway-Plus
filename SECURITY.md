# Security

Gaming PC loopback is not raw-device isolation. In live Sunshine testing, original
remote mouse reports remained visible through Raw Input while ordinary window
messages received only the Pico clicks. A Raw Input application may observe
both sources. Do not use this mode as a claim of hardware-only input origin.

HIDway delivers keyboard and mouse actions to a target computer through USB. Access to an authorized sender or relay can therefore become control of that target. Treat the complete input path as privileged, even though the software normally runs without administrator rights.

Updated 2026-10-29 for the input preview and observed hardware limitations. This document describes source controls and known limits; it is not a certification of every deployed machine or untested input source.

The confirmed AION2 same-PC session required a manually approved elevated HIDway
launch to match the game's integrity level. Elevation gives the client broader
local access; the installer and client do not elevate automatically or change
UAC settings. Normal launches remain unelevated. A separately launched lower-
integrity Monitor may be unable to send replay IPC to an elevated client; close
that Monitor and launch the companion from the elevated client when needed.

## Trust boundaries

| Boundary | Trust and protection |
|---|---|
| Local input → Windows client | Selected sources are accepted while armed; injected flags are hints, not application authentication |
| Client → relay | Private routing, source allow-list and optional shared-key authenticated encryption |
| Relay → Pico UART | Physical access is trusted; CRC detects corruption, not malicious commands |
| Pico → target USB | Target accepts the device as a keyboard/mouse; HIDway does not constrain target actions |
| Repository/update service → installed relay | Repository/ref and administrator configuration are trusted; builds/tests and rollback reduce operational failure |

Virtual / remote enables input generated by other local software, including remote-control and accessibility software. It cannot limit acceptance specifically to AnyDesk. A virtual-HID driver may appear physical. Pico VID/PID filtering is a routing heuristic, not a security identity.

## Deployment requirements

- Bind the relay to its intended private address and allow only the intended sender. Apply network access rules for UDP 47800 to those peers. Tailscale is external to HIDway and must be configured independently.
- Do not expose a serial-connected bare daemon using its permissive defaults. Without `--allow` or encryption it accepts valid commands from any reachable source. The source warning does not prevent this configuration.
- Enable matching shared-key encryption when application-level authentication is required. Generate an independent random 32-byte key using a cryptographic generator; do not reuse example keys. Empty settings mean plaintext mode.
- Restrict access to `hidway.ini` and relay key/config files. The client stores the hexadecimal key as plaintext; it is not protected by DPAPI. Keep keys out of source control, screenshots and support reports. Rotate both ends together after suspected exposure.
- Trust the configured update repository and its maintainers. Use reviewed releases. Keep root-owned configuration and service files writable only by administrators.
- Test physical panic/disarm and failure recovery on the actual setup before relying on remote or loopback input. Maintain another way to stop the input path while validating it.

See [relay configuration](docs/RELAY.md) for concrete settings. The Windows client
sets its working directory to its executable folder before loading the adjacent
configuration; access to that folder and its plaintext key remains trusted.

## Implemented controls

The relay checks an optional source-IP allow-list, packet sizes/types, crypto mode and authentication before acting. Encrypted commands use XChaCha20-Poly1305 with a 32-byte shared key and random nonces. Command timestamps enforce increasing order, a clock window and a relay-start floor. Plaintext and encrypted modes are not automatically mixed.

The relay limits ordinary command rate, bounds ordered serial output, sends RELEASE after input silence and retries disconnected serial devices. Pico independently releases after input silence and has a hardware watchdog. Receiver queue overflow or expired work releases and latches an input fault; new peers propagate that fault to the client. Disarm sends repeated RELEASE packets. These controls do not prove that the Windows capture state is correct or that every UDP transition reached USB.

Managed Linux deployment separates build/runtime users and applies systemd privilege, filesystem, device and resource restrictions. Update activation normally waits for idle input; failed health checks can roll back. Root-level service changes are applied separately. Vendored code and CI dependencies have explicit versions/revisions in source, but this review did not perform a current vulnerability-advisory audit.

## Known limitations

The optional standalone input monitor observes local device metadata, counts
and transient held state. Background counting is visible and enabled by
default. Optional injection-flag hooks always pass events onward. The monitor
has no network code or input-injection path. It stores names/source labels and
optional numeric summaries locally. Explicit Record saves key/button identities,
timestamps and movement in unencrypted local files; these can reveal typed text.
Recording is visible, off by default, bounded and never part of release payloads.
Replay is confirmed in the client, uses normal Pi/Pico output with live capture
off, and releases on Stop/PANIC/completion or existing transport faults. Device
names, bus classification and user labels are not authenticated identities.

The Windows wizard installs per user, preserves live configuration, checks the
payload hashes and refuses locked binaries. SHA-256 is a corruption check, not
publisher authentication; preview binaries/scripts are unsigned. Pi installation
uses visible OpenSSH host verification/login/sudo and trusts the configured public
repository main branch. The wizard does not store credentials. Firmware selection
checks BOOTSEL family and still requires the user to identify W/non-W hardware.

The Windows **Check for updates** path uses a fixed public GitHub repository.
When HIDway opens it makes one unauthenticated, read-only request for that
repository's latest release (`update_check = 0` in `hidway.ini` turns it off);
downloading and installing happen only after the user presses Update now or
uses the Updates window. It refuses drafts/prereleases, ambiguous assets, wrong URLs, missing
digests, oversized archives, traversal/duplicate entries and payload/version
mismatches. The outer GitHub asset SHA-256 and internal manifest are checked
before the paired installer runs. Applying refuses running client/Monitor
processes; it never terminates input sessions, elevates or flashes hardware.
Downloaded packages remain in the user's local update cache. This trusts GitHub,
the repository and maintainer account; SHA-256 is not a signed publisher identity
or protection against a malicious release. See [updates](docs/UPDATES.md).

1. **Driver-dependent capture:** the 2026-10-28 implementation fixes source overlap, removes keyboard echo/time guesses, rejects Unicode packets before scan mapping and adds generation/enqueue/age checks. Injection flags still do not identify applications, and virtual HID drivers can appear physical. Same-machine native/Pico overlap and remote-driver behavior require hardware acceptance.
2. **Capture loss:** Windows can silently remove a slow low-level hook. Virtual-only mode lacks the exclusive mode's foreground checks; healthy network traffic can continue carrying stale held state. Transport watchdogs cannot detect that case. [Windows hook behaviour](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelmouseproc).
3. **Initial connection failure:** corrected on 2026-10-27. The no-reply deadline starts at ARM even if no status was ever received. The configurable timeout can still be disabled explicitly.
4. **Status freshness:** corrected on 2026-10-27 using session validation, echoed-client timestamp ordering and an age limit. Duplicate/older replies do not refresh health; a delayed reply's lease uses its request time. This does not remove real network delay or authenticate plaintext independently of its network.
5. **Update authenticity:** release tags and archive hashes are not a signed update chain. The Linux updater trusts its repository/ref and does not wait for a remote CI success result before building locally. The Windows updater installs published binary packages; the repository release workflow gates publication on CI, but the client does not independently attest that workflow. The Makefile dependency omission was corrected; isolated Linux build/common, relay fail-safe and installer tests passed on 2026-10-27.
6. **OS boundaries:** Secure Desktop, logon, integrity levels and remote-input drivers have different rules. Lock/power notifications do not establish reliable capture-loss detection across every secure-desktop transition. Do not assume ordinary desktop hooks capture those screens. [Windows input restrictions](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput).
7. **Bounded cancellation:** 100 ms local capture/journal/sender backlog and receiver queues are cancelled rather than replayed. A genuine GUI/USB/UART stall can therefore disarm. UDP has no per-edge acknowledgment/retry; arrived-edge preservation is not a delivery guarantee.
8. **Multiple controllers:** the relay can permit up to eight exact IPv4 peers, but only one active input session owns it. Configure only intended controllers. Fresh ARM sessions retire earlier sessions; this prevents delayed takeover, not malicious access by an already authorized/key-holding peer.

## Reporting a vulnerability

Do not publish working credentials, private addresses, remote-access information or exploit details that put a live target at risk. Use the repository's private vulnerability-reporting channel if enabled; otherwise arrange a private maintainer contact before sharing sensitive details. This source tree does not establish a dedicated security email or a supported-release response commitment.

Provide the affected revision, operating system, topology, selected sources, encryption mode, a minimal reproduction and expected/actual behaviour. Remove secrets from logs. Separate a source-level finding from an observed deployment issue.

## Validation before release

Require Windows and Linux builds, common tests, relay fail-safe tests and installer checks. Add capture-state regression tests, authenticated reply replay tests and an actual-device matrix covering key overlap, button release, disconnects, hook loss, lock/UAC transitions and source changes. Run a sustained hardware session and confirm release behaviour independently at the target. The current passing shared tests do not cover all of these conditions.
